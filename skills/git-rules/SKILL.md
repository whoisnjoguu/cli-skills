# Git delivery rules

Turn a finished change into a branch, a sequence of focused commits, and a pull request that a reviewer can trust, without ever leaving the repository in a worse state than you found it. Every rule has a stable ID, a level, a default severity, and a **Verify** step.

The person who asked for the change owns it. Their identity goes on the commits, their repository's conventions override this skill's defaults, and anything that cannot be undone needs their explicit say-so.

## Operating modes

This skill is guidance by default. Loading it does not authorize committing, pushing, or opening a pull request.

- **Guidance mode** (default): answer questions about branch names, commit splitting, messages, PR descriptions, rebasing, or safety, and cite rule IDs.
- **Delivery mode**: the user asks you to commit, push, or open a pull request for work that is done or that you are doing. Follow [Delivery workflow](#delivery-workflow).
- **Audit mode**: the user explicitly asks to audit, review, or grade a branch, pull request, or recent history against these rules, or requests a report. Follow [AUDIT.md](AUDIT.md) and produce `findings.json` and `REPORT.md`.

If a request could mean more than one mode, ask one short question before running any command that writes.

## Core principles

1. **The repository's convention wins.** Read `CONTRIBUTING.md`, commitlint or hook configuration, the PR template, and recent `git log` before writing anything. Match what is there; fall back to these defaults only when nothing is established ([GIT-WRK-002](WORKFLOW.md#git-wrk-002-discover-and-follow-the-repositorys-conventions)).
2. **One change per commit, one purpose per branch.** A commit is the unit of review, bisect, and revert. Separate refactors from behavior, leave unrelated fixes for another branch, and stage by hunk ([COMMITS.md](COMMITS.md)).
3. **The message explains why.** Imperative subject around 50 characters, blank line, body wrapped at 72 that gives the problem and the reasoning. The diff already shows how ([COMMIT-MESSAGES.md](COMMIT-MESSAGES.md)).
4. **The human is the author.** Commits carry the user's identity. No `Co-authored-by` for assistants, no "Generated by", no tool signatures in commits, titles, descriptions, or comments ([GIT-MSG-011](COMMIT-MESSAGES.md#git-msg-011-never-attribute-the-commit-to-an-ai-agent-or-tool), [GIT-PR-008](PULL-REQUESTS.md#git-pr-008-keep-agent-attribution-and-self-reference-out-of-the-pull-request)).
5. **A pull request is a request for someone's time.** Small, single-purpose, with a title that works as a commit subject and a description that says what, why, and how it was verified ([PULL-REQUESTS.md](PULL-REQUESTS.md)).
6. **Never destroy what you did not create.** No rewriting published history, no plain `--force`, no `reset --hard` or `clean` over the user's work, no bypassed hooks, no changed identity or remotes ([HISTORY-AND-SAFETY.md](HISTORY-AND-SAFETY.md)).

## Delivery workflow

1. **Preflight.** Run the read-only checks in [WORKFLOW.md](WORKFLOW.md#preflight-checklist): current branch and upstream, dirty files, remotes, identity, templates, hook and lint configuration, last 15 to 30 subjects. Note the detected conventions.
2. **Branch.** Fetch, then create a topic branch from the up-to-date base with a lowercase kebab-case name in the repository's pattern ([BRANCHES.md](BRANCHES.md)). Never work on the default branch.
3. **Plan the commits.** Before staging, list the logical changes in the diff and the order they should land: refactor, behavior with tests, docs, generated output ([COMMITS.md](COMMITS.md#splitting-work-into-commits)).
4. **Commit each change.** Stage by path or hunk, read `git diff --staged`, run the smallest relevant check, write the message via editor, heredoc, or `-F` ([COMMIT-MESSAGES.md](COMMIT-MESSAGES.md#shape-of-a-message)), and confirm with `git log -1 --format=%B`.
5. **Clean up locally.** Squash fix-ups and wip commits with `--autosquash` before the first push. Run the fuller test suite.
6. **Self-check.** Run the message checks in [CONVENTIONS.md](CONVENTIONS.md#useful-commands): subject lengths, imperative mood, no agent attribution, no conflict markers, `git diff --check`, and commitlint if present.
7. **Publish.** `git push -u origin HEAD`, then `gh pr create` with a title that follows the subject rules and a body written to a file that fills the template or the skeleton in [PULL-REQUESTS.md](PULL-REQUESTS.md#description-skeleton). Use `--draft` when work remains.
8. **Report.** Tell the user the branch name, the commit list, the pull request URL, how the change was verified, and anything you could not do or had to assume. Then stop; merging is their call unless they delegated it.

## Anti-patterns

- `git add -A && git commit -m "updates"` on whatever happens to be in the tree.
- One commit titled "Implement feature" that contains a refactor, the feature, a formatter run, and a fix to an unrelated test.
- `Co-authored-by: <assistant>` or "Generated with <tool>" in a commit or pull request body.
- A `feat:` prefix in a repository whose history has never used Conventional Commits, or a plain subject in one that enforces them.
- `git commit --no-verify` because the hook was "slow" or "flaky".
- Committing on `main` and then trying to open a pull request.
- `git push --force` to a branch someone else has pulled, or during review in a project that expects follow-up commits.
- `git reset --hard` or `git stash drop` to "clean up" the user's uncommitted changes.
- A pull request description that is empty, says "see commits", or leaves template placeholders in place.
- Branch names such as `patch-1`, `copilot/fix`, `alice-wip`, or `Fix_Bug`.
