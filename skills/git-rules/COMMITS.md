# Commits

Load this file when deciding how to split work into commits and what to stage in each. A commit is the unit of review, bisect, cherry-pick, and revert. Commits that are focused and self-contained make every one of those operations cheap; commits that bundle unrelated edits make all of them expensive.

## Splitting work into commits

Plan the commits before writing the first one. A good sequence for a typical feature:

1. Preparatory refactor that changes no behavior (rename, extract, move).
2. The behavior change itself, with its tests.
3. Documentation and changelog for the change.
4. Generated files regenerated by the change, if the project commits them, in the same commit as the source that drives them.

Stage per commit with `git add -p` or by path, and read `git diff --staged` before each commit. Use `git commit --fixup` and `git rebase -i --autosquash` to repair an earlier commit on a branch you have not pushed, instead of adding a "fix previous commit" on top.

## Rules

### GIT-CMT-001: Make each commit one logical change

- **Level:** must
- **Severity:** high
- **Check:** static
- **Source:** <https://git-scm.com/book/en/v2/Distributed-Git-Contributing-to-a-Project>

A commit should do one thing that can be described in a single subject line without "and". Mixing a bug fix with a feature, or two unrelated fixes, means neither can be reverted or cherry-picked alone and the reviewer has to untangle them.

**Verify:** For each commit in `git log <base>..HEAD`, the subject describes the whole diff, and no hunk belongs to a different change than the subject names.

### GIT-CMT-002: Leave the tree building and tests passing at every commit

- **Level:** should
- **Severity:** medium
- **Check:** static, manual
- **Source:** original

Each commit should compile and pass the tests that exist at that point, so that `git bisect` lands on real culprits and any commit can be checked out safely. Do not split a change so that an intermediate commit references code introduced later.

**Verify:** Checking out each commit on the branch and running the project's build and test command succeeds, or the pull request states which intermediate commits are intentionally not independently buildable and why.

### GIT-CMT-003: Separate refactoring and formatting from behavior changes

- **Level:** should
- **Severity:** medium
- **Check:** static
- **Source:** original

A rename, a move, a reformat, or an import reorder produces a large diff with no semantic content. Put it in its own commit so the behavior change that follows is a small diff a reviewer can actually read. Never run a formatter over files the change does not otherwise touch.

**Verify:** No commit mixes a pure refactor or reformat with a change in behavior; files that appear in the diff only because of formatting are in a dedicated commit or absent.

### GIT-CMT-004: Commit generated files with the change that regenerates them

- **Level:** should
- **Severity:** low
- **Check:** static
- **Source:** original

When the project commits generated output (lockfiles, checklists, snapshots, schema or protobuf output), regenerate it in the same commit as the source change so that commit is consistent and CI passes on it. Large regenerations with no source change (tool upgrades) get their own commit.

**Verify:** Running the project's generate command at each commit produces no diff, and no commit contains generated changes without their driving source change unless the subject says it is a regeneration.

### GIT-CMT-005: Stage deliberately and review the staged diff before committing

- **Level:** must
- **Severity:** high
- **Check:** manual
- **Source:** original

Stage by path or by hunk, never with `git add -A` or `git commit -a` in a tree that may contain files you did not intend. Read `git diff --staged` and `git status` before every commit to confirm that only the intended files and hunks are included and nothing is missing.

**Verify:** The transcript shows `git diff --staged` or `git status` immediately before each commit, and no commit contains files or hunks unrelated to its subject.

### GIT-CMT-006: Never commit secrets, credentials, or personal configuration

- **Level:** must
- **Severity:** high
- **Check:** static, probe
- **Source:** <https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning>

API keys, tokens, passwords, private keys, `.env` files, cloud credentials, and local IDE or shell configuration never belong in history. Check the staged diff for them explicitly, and keep patterns for them in `.gitignore`. If a secret is already committed, see [HISTORY-AND-SAFETY.md](HISTORY-AND-SAFETY.md).

**Verify:** `git diff <base>...HEAD` contains no credential-shaped strings (long random tokens, `-----BEGIN ... PRIVATE KEY-----`, `AKIA...`, `ghp_...`, `password=`), no `.env*` files, and no user-specific config such as `.idea/`, `.vscode/settings.json`, or `.DS_Store`, unless the repository tracks them deliberately.

### GIT-CMT-007: Keep build artifacts and dependencies out of commits

- **Level:** must
- **Severity:** medium
- **Check:** static
- **Source:** original

Compiled output, `node_modules`, virtualenvs, coverage reports, caches, and logs are not source. If one shows up in `git status`, add the pattern to `.gitignore` in a focused commit rather than committing the artifact or ignoring the problem.

**Verify:** `git diff --stat <base>...HEAD` lists no files under build, dist, target, node_modules, coverage, or cache directories, and no binaries, unless the repository documents vendoring them.

### GIT-CMT-008: Leave unrelated problems for a separate change

- **Level:** must
- **Severity:** medium
- **Check:** static
- **Source:** <https://google.github.io/eng-practices/review/developer/small-cls.html>

Fixing a typo, a lint warning, or a pre-existing bug in a file you happen to be editing widens the diff and hides the real change. Note the issue for the user, or make a separate branch and pull request. The exception is a bug caused by or tightly coupled to the change you are making.

**Verify:** Every hunk in the branch diff is required by the task as described in the pull request; incidental fixes are absent or in a separate pull request.

### GIT-CMT-009: Keep commits small enough to review in one sitting

- **Level:** should
- **Severity:** medium
- **Check:** static
- **Source:** <https://google.github.io/eng-practices/review/developer/small-cls.html>

Prefer a sequence of small commits over one large one. As a rough guide, a commit touching more than about 400 changed lines of hand-written code, or more than a dozen files for different reasons, is a candidate for splitting. Mechanical changes (renames, generated files) may be large but should then be nothing else.

**Verify:** `git show --stat <commit>` for each commit shows a diff a reviewer can read in a few minutes, or the commit is a labeled mechanical change.

### GIT-CMT-010: Squash fix-up and work-in-progress commits before publishing

- **Level:** should
- **Severity:** low
- **Check:** static
- **Source:** <https://git-scm.com/book/en/v2/Git-Tools-Rewriting-History>

"wip", "fix typo", "oops", and "address review" commits are noise once the branch is published. On a branch nobody else has pulled, fold them into the commits they correct with `git commit --fixup` and `git rebase -i --autosquash` before the first push. After publishing, follow the repository's convention: many projects prefer visible follow-up commits during review and squash on merge.

**Verify:** `git log --oneline <base>..HEAD` at pull request creation contains no fix-up, wip, or placeholder subjects.

### GIT-CMT-011: Keep renames detectable

- **Level:** consider
- **Severity:** low
- **Check:** static
- **Source:** original

Move or rename a file in one commit and edit its contents in the next, so `git log --follow` and `git blame` keep the file's history. A rename combined with heavy edits in the same commit shows up as a delete plus an add.

**Verify:** `git show --stat -M <commit>` reports renames with a high similarity index rather than a delete and an add for files that were moved.

### GIT-CMT-012: Respect the project's whitespace, line ending, and encoding settings

- **Level:** should
- **Severity:** low
- **Check:** static
- **Source:** original

Honor `.editorconfig` and `.gitattributes`. Do not introduce trailing whitespace, mixed indentation, CRLF in an LF repository, or a BOM. Whitespace-only diffs hide real changes and trigger needless conflicts.

**Verify:** `git diff --check <base>...HEAD` reports nothing, and `git diff -w --stat` matches `git diff --stat` for hand-written files.
